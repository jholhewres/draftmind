# Contributing to Draftmind

Thanks for helping. Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and the ADRs in [docs/adr/](docs/adr/) before changing behaviour; an ADR that no longer fits is reopened with a new ADR, not edited silently.

## Setup

Requirements: Go 1.27+, Node 22+, pnpm 10, Docker, golangci-lint v2. Python 3 with Pillow and numpy only to rebuild test fixtures.

```sh
cp .env.example .env   # OPENROUTER_API_KEY is optional for most work
make setup
make db-up
make sync              # first data load from dotaconstants, the game's data feed and OpenDota
make dev
```

`make help` lists every target.

## Curated data

`api/data/item_counters.json` holds the counter tags (ADR-0011): which items answer which tag, the tags a hero brings by slug, and the tags each dotaconstants role brings. It is the only place these opinions live; never hardcode them in Go.

- Use dotaconstants item keys and hero slugs; names the current patch lacks are skipped.
- Tags are lower-case words with underscores.
- Bump `version` on every change, then run `make sync` (or `go -C api run ./cmd/draftmind sync builds`) to load it.
- Explain the change in the pull request: these tags bias the situational items every player sees.

## Tests

Run these before opening a pull request; CI runs the same:

```sh
make db-up
make test lint
```

- `make test`: Go tests (each database test gets its own throwaway database on the compose Postgres, or on `TEST_DATABASE_URL`; they skip when Postgres is down) and Vitest.
- `make lint`: `go vet`, golangci-lint, oxlint and `tsc`.
- Tests sit next to the code (`*_test.go`, `*.test.tsx`). External HTTP calls are tested against `httptest` servers or recorded fixtures, never the live API.
- `make bench-photo` reads every photo in `api/testdata/photos` with both photo readers, live. It needs `OPENROUTER_API_KEY` and costs a few cents; run it when you change the photo reader and paste the result table in the pull request.

### Visual tests (e2e)

`make e2e` runs the Playwright specs in `web/e2e/` at phone (390x844) and desktop (1280x800) sizes against a mocked API, and compares screenshots with the baselines in `web/e2e/__screenshots__/`.

- The baselines are **Linux only** (`*-linux.png`) and depend on Chromium's font rendering, so they are not checked in CI and may differ on macOS or another distribution. Run them on Linux.
- After an intended UI change, rewrite the baselines with `make e2e-update`, look at every changed image, and commit them with the change.
- A new spec mocks every API route it uses (`web/e2e/fixtures.ts`); it never needs the Go server or a model.

### Fixtures

The synthetic pick-screen photos and the end screen are generated by the scripts in `scripts/fixtures/`; see [api/testdata/photos/README.md](api/testdata/photos/README.md). Real game photos are never committed, only their expected drafts (`real/*.json`).

## Product rules

- **Game facts come from the synced database, never from code.** Heroes, items, abilities, matchups and patch notes are read from the tables `make sync` fills. Do not hardcode a hero name, id, item or number in production logic, and never let model output introduce an entity that is not in the database for the current patch.
- **The LLM writes, Jev decides, the code executes** (ADR-0003). Code builds the candidates, Jev chooses, the writer only writes text from the decided result. Every model path fails open to the code ranking.
- **Trademark:** never use "Dota" in the product name, logo or domain, and keep the Valve trademark and fair-play note in the UI footer.
- **Translatable UI.** Every user-facing string goes through the message catalogs in `web/src/locales/` with a key in both `en.ts` and `pt-BR.ts`. Logic makes no locale assumptions; server text that reaches the player (e-mails, coach answers) follows the player's language.
- Prefer the standard library; add a dependency only with a clear reason.
- Secrets live only in your local `.env`. Never commit, log or paste a key.

## Database

Migrations live in `api/internal/db/migrations/`, numbered and applied once in name order. Never edit a migration that has been merged; add a new one.

## Commits and pull requests

- Small, thematic commits in English with a conventional prefix: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `ci:`.
- The subject says what changes in plain words, in the imperative, without a trailing period.
- No co-author or attribution trailers.
- One topic per pull request; describe what changed, why, and how you tested it.

Coding agents follow [AGENTS.md](AGENTS.md).
